# แผนทดสอบและกรณีความล้มเหลว

## 1. หลักการ

ใช้ข้อมูลจำลองที่ติดป้ายว่าเป็นข้อมูลทดสอบในชุดทดสอบเท่านั้น ห้ามนำผลจำลองไปแสดงเป็น LIVE หรือสร้าง session/คำสั่งเปิดประตูจริง การทดสอบอุปกรณ์จริงต้องทำในพื้นที่และช่วงเวลาที่ได้รับอนุญาต พร้อมมี รปภ. ควบคุม

## 2. ตารางกรณีทดสอบ

| ID | กรณี | ผลที่คาดหวัง / เกณฑ์ผ่าน |
|---|---|---|
| IMG-01 | ภาพชัด รถผ่านกล้องที่ map ชั้นแล้ว | บันทึก camera, timestamp, plate, confidence, floor และ event_id; แสดงแหล่งข้อมูล |
| IMG-02 | กลางคืน/ย้อนแสง/ภาพเบลอ | confidence ลดหรือ OCR_FAILED; เข้าคิวตรวจสอบ; ไม่อนุมัติไม้กั้นอัตโนมัติ |
| IMG-03 | ป้ายถูกบังหรืออ่านไม่ได้ | เก็บผล OCR failure พร้อม evidence reference ถ้ามี; ไม่สร้าง plate ปลอม |
| IMG-04 | CiRA ส่ง event ซ้ำ | deduplicate ด้วย event_id/กติกาที่ตกลง; ไม่สร้าง session หรือ event ซ้ำ |
| FLR-01 | กล้องชั้น 1 ตรวจได้ แต่ไม่พบหลักฐานช่อง | แสดงชั้นล่าสุดที่ตรวจพบและช่อง UNKNOWN |
| FLR-02 | กล้องชั้น 1 และชั้น 2 ตรวจรถต่อเนื่อง | ปรับชั้นเมื่อ event ผ่าน validation; เก็บประวัติชั้นและเวลา |
| FLR-03 | กล้องลำดับถัดไปขาดหาย/ข้อมูลผิดลำดับ | ไม่เขียนทับตำแหน่งโดยไม่ตรวจ; แสดง stale/unknown หรือให้ review |
| SLOT-01 | HC-SR04 ค่าระยะชัดและสดว่าช่องว่าง | `AVAILABLE` และนับช่องว่างได้ |
| SLOT-02 | Sensor ตรวจพบรถ | `OCCUPIED` พร้อม timestamp/source |
| SLOT-03 | Sensor หยุดส่งเกิน timeout | เปลี่ยนเป็น `UNKNOWN`/`ERROR`; ไม่นับเป็นว่าง |
| SLOT-04 | Sensor และแหล่งภาพที่ยืนยันแล้วขัดกัน | `CONFLICT`; แจ้งผู้ปฏิบัติงาน ไม่เลือกผลเอง |
| SLOT-05 | รถหลายคันผ่านและหลายช่องเปลี่ยนในหน้าต่างเดียวกัน | ไม่ผูกทะเบียนกับช่องเมื่อมีหลาย candidate; แสดงช่อง UNKNOWN |
| NET-01 | Internet ดับแต่ LAN/broker/backend ยังอยู่ | ส่วนภายใน LAN ทำงานได้ตามที่ติดตั้ง; cloud dependency แสดง unavailable |
| NET-02 | MQTT broker หยุด | สถานะ broker offline, ข้อมูลค้างถูกระบุ stale, ไม่มีการเปิดประตู/สร้างสถานะว่างปลอม |
| NET-03 | Backend/DB หยุดแล้วกลับมา | ระบุช่วงขาดข้อมูล; รับข้อมูลซ้ำได้อย่างปลอดภัย; ไม่สร้าง session ซ้ำ |
| NET-04 | event ล่าช้าหรือ timestamp ผิด | ทำเครื่องหมาย late/invalid; ไม่ใช้ event เก่าเขียนทับสถานะสดโดยไม่มีกฎ |
| AUTH-01 | Student/Teacher ขอข้อมูลบัญชีอื่นผ่าน API | ปฏิเสธด้วย authorization error และไม่มีข้อมูลรั่ว |
| AUTH-02 | Security ใช้ endpoint Admin | ปฏิเสธตาม role; บันทึกการปฏิเสธตามนโยบาย |
| AUD-01 | เพิ่ม/แก้ไขทะเบียนหรือข้อมูลบุคคล | บันทึก actor, เวลา, entity, ค่าเดิม/ใหม่ตามนโยบาย |
| PLATE-01 | เพิ่มทะเบียนที่ผูกกับบัญชีอื่นแล้ว | ปฏิเสธการผูกซ้ำและแจ้งข้อความที่ไม่เปิดเผยข้อมูลเจ้าของเดิมเกินจำเป็น |
| CHAT-01 | รปภ. ส่งข้อความถึงผู้ใช้ | ข้อความอยู่ใน conversation ที่ถูกต้อง มีผู้ส่ง เวลา และสถานะส่ง |
| GATE-01 | AI อ่านทะเบียนตรงกับบัญชี | สร้าง review event เท่านั้น ไม่ publish OPEN/CLOSE |
| GATE-02 | รปภ. อนุมัติคำสั่งพร้อมเหตุผล | บันทึกผู้อนุมัติ เหตุผล เวลา command_id และสถานะส่งคำสั่งแยก |
| GATE-03 | คำสั่งถูกส่งแต่ controller ไม่ ACK | แสดง command pending/timeout; ห้ามแสดงว่าไม้กั้นเปิด |
| GATE-04 | Controller ACK แต่ไม่มี physical feedback | แสดง ACK แยกจากสถานะจริง; ห้ามยืนยันว่าประตูเปิด |
| GATE-05 | ไม้กั้นเปิดแต่ไม่มี passage evidence | ไม่สร้าง session/ยืนยันรถผ่านจนมีหลักฐาน passage ที่กำหนด |
| UI-01 | API ไม่ตอบ/ข้อมูลเก่า | UI แสดง offline/stale และเวลา last update; ไม่แสดง badge LIVE ผิดจริง |

## 3. หลักฐานที่ต้องเก็บ

- เวลาและ environment ของการทดสอบ (จำลอง/อุปกรณ์จริง)
- payload ที่ลบข้อมูลส่วนบุคคลหรือปกปิดทะเบียนตามความเหมาะสม
- ภาพหน้าจอ/ผล API/log ที่แสดงสถานะคาดหวัง
- firmware/config version และรหัสอุปกรณ์ (ไม่ใส่ secret)
- ผ่าน/ไม่ผ่าน, ผู้ทดสอบ, ปัญหาที่พบ, วิธีแก้และผลทดสอบซ้ำ

## 4. เกณฑ์พร้อมสาธิต

อย่างน้อยต้องสาธิตกรณีภาพชัด, ภาพอ่านไม่ได้, ชั้นรู้แต่ช่องไม่รู้, sensor offline, ผู้ใช้เห็นเฉพาะข้อมูลของตน, AI ไม่เปิดประตูเอง และคำสั่งที่ไม่มี ACK/feedback ไม่ถูกแสดงว่าเปิดแล้ว ต้องระบุชัดว่าการสาธิตใดเป็นข้อมูลจำลองและส่วนใดใช้อุปกรณ์จริง
