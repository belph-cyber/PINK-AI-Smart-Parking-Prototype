# ข้อกำหนดระบบ PINK AI Smart Parking

เวอร์ชัน 1.0 · 21 พฤศจิกายน 2569

## 1. วัตถุประสงค์และปัญหา

ระบบนี้ช่วยระบุว่ารถที่ผ่านจุดตรวจอยู่ชั้นใด และช่วยประเมินสถานะช่องจอดในอาคารที่กล้องไม่สามารถเห็นทุกช่องพร้อมกัน กล้องประจำทางขึ้นแต่ละชั้นรับภาพและส่งให้ CiRA ประมวลผลทะเบียนรถ ส่วนเซนเซอร์ระยะรายช่องรายงานว่ามีวัตถุ/รถอยู่ในช่องหรือไม่ ระบบรวมหลักฐานเหล่านี้เพื่อแสดงข้อมูลที่เหมาะสมแก่ผู้ใช้และเจ้าหน้าที่

โครงงานเน้น **การรับภาพ การส่งต่อภาพ/ผลตรวจ และการประเมินคุณภาพหลักฐานภาพ** ไม่ใช่เพียงหน้าจอเว็บจัดการลานจอดรถ

## 2. ผู้ใช้และสิทธิ์

| บทบาท | ข้อมูล/การทำงานที่อนุญาต |
|---|---|
| นักศึกษา | ดูทะเบียน สถานะรถ และประวัติเข้าออกของบัญชีตนเอง; เพิ่มและจัดการทะเบียนของตนเอง |
| อาจารย์ | สิทธิ์เช่นเดียวกับนักศึกษา ดูเฉพาะข้อมูลของตนเอง |
| รปภ. | ตรวจเหตุการณ์ที่ต้องตรวจสอบและสื่อสารกับผู้ใช้ผ่านแชท; ปฏิบัติตามสิทธิ์สั่งงานประตูที่กำหนด |
| แอดมิน | จัดการบัญชี/ข้อมูลระบบและตรวจ audit log ตามสิทธิ์ |
| ผู้ดู Kiosk | ดูสถานะภาพรวมที่ไม่เปิดเผยข้อมูลส่วนตัว |

การซ่อนเมนูในหน้าเว็บไม่ถือเป็นการควบคุมสิทธิ์ ต้องตรวจสิทธิ์ที่ API ด้วย

## 3. ข้อกำหนดตามหัวข้อวิชา

| หัวข้อ | ข้อกำหนด |
|---|---|
| ปัญหา | ตรวจชั้นและสถานะช่องจอดในอาคารที่กล้องไม่เห็นทุกช่อง |
| Input / Sensor | (ก) กล้องที่ทางขึ้น/จุดผ่านชั้น รับภาพรถเพื่อส่งเข้า CiRA (ข) HC-SR04 หรือเซนเซอร์ระยะที่เลือกจริง ติดช่องจอดและอ่านผ่าน ESP32 |
| เหตุผลที่เลือก | กล้องดูบริเวณจุดผ่านที่ควบคุมมุมมองได้และใช้ LPR ได้; เซนเซอร์รายช่องช่วยตรวจช่องที่กล้องมองไม่เห็น ทั้งสองชนิดทำหน้าที่ต่างกันและเสริมกัน |
| ประมวลผล | ตรวจรถ/ป้ายทะเบียน, อ่านจังหวัดตามที่ระบบรองรับ, เก็บค่าความมั่นใจ/ภาพอ้างอิง/เวลา/รหัสกล้อง; แปลงผลเซนเซอร์เป็นสถานะช่อง; ประเมินความใหม่และความสอดคล้องของหลักฐาน |
| การระบุชั้นและช่อง | กล้องที่ผ่านให้หลักฐานชั้นล่าสุด; เซนเซอร์ให้สถานะช่อง; จะผูกทะเบียนกับช่องได้เมื่อเหตุการณ์มีหลักฐานจับคู่ชัดเจนเท่านั้น หากไม่ชัดให้แสดงชั้นได้แต่ช่องเป็น UNKNOWN |
| Output / Actuator | หน้าจอเว็บ/API, แจ้งเตือนให้ รปภ. ตรวจสอบ, ไฟแสดงผลถ้ามี; การควบคุมไม้กั้นเป็นคำสั่งแยกที่ผู้มีสิทธิ์อนุมัติ ไม่สั่งเปิดจากผล AI โดยอัตโนมัติ |
| การสื่อสาร | MQTT สำหรับ telemetry/event ระหว่าง CiRA/ESP32/Backend ตาม broker จริง; HTTP/REST สำหรับเว็บกับ API; กล้องใช้ RTSP/MJPEG หรือวิธีของอุปกรณ์จริง ต้องบันทึกผลยืนยันหน้างาน |
| การเก็บ/แสดง | เก็บผู้ใช้ ทะเบียน เหตุการณ์ตรวจพบ ชั้น สถานะช่อง แหล่งข้อมูล เวลา confidence การอนุมัติ/คำสั่ง/ผลตอบกลับ และ audit log; ผู้ใช้เห็นเฉพาะของตนเอง; ภาพต้องมีสิทธิ์และอายุเก็บที่กำหนด |
| Internet/Server ล้มเหลว | หาก broker และอุปกรณ์อยู่ LAN เดียวกัน การรับค่าภายในอาคารอาจทำต่อได้; เมื่อ Backend ล้มเหลวให้แสดง offline, คิวส่งซ้ำเมื่อกลับมา และป้องกัน event ซ้ำ; ผู้ใช้ต้องเห็นเวลาข้อมูลล่าสุดและห้ามตีความข้อมูล stale เป็น live |
| ความผิดปกติ | OCR ไม่สำเร็จ/ความมั่นใจต่ำ, ภาพขาดหาย, กล้อง offline, sensor timeout/ค่าแกว่ง, MQTT/API/DB offline, ข้อความซ้ำ/ผิดลำดับ, ข้อมูลช่องขัดแย้ง, รถไม่มี exit evidence, คำสั่งไม่มี ACK หรือ physical feedback |
| Parameter | resolution, frame rate, exposure/focus, ROI, LPR threshold, จำนวนเฟรมยืนยัน, debounce/cooldown, sensor threshold/filter, freshness timeout, event correlation window, retry/backoff, MQTT QoS; ปรับได้เฉพาะผู้ดูแลที่กำหนด |
| Diagram | Architecture, sequence, data-state diagram และ network/offline behavior อยู่ใน `SYSTEM_DESIGN.md` |

## 4. ข้อกำหนดด้านสถานะและความปลอดภัย

- สถานะช่องประกอบด้วย `AVAILABLE`, `OCCUPIED`, `RESERVED`, `UNKNOWN`, `ERROR`, `CONFLICT`.
- หลักฐานหาย หมดอายุ หรืออุปกรณ์ offline ต้องเป็น `UNKNOWN` หรือ `ERROR` ตามสาเหตุ ไม่ใช่ `AVAILABLE`.
- ป้ายกำหนดสิทธิ์ให้จอดจะยังไม่ถือเป็นระบบจอง จนกว่าจะยืนยันว่ามีวัน/เวลาเริ่มและสิ้นสุดการจอง.
- ผู้ใช้เพิ่มทะเบียนได้ตามข้อกำหนดโครงการโดยไม่รออนุมัติ แต่ระบบต้องป้องกันการผูกทะเบียนเดียวกับหลายบัญชี บันทึกการเปลี่ยนแปลง และมีทางให้ รปภ. แจ้งตรวจสอบ/ระงับเมื่อพบข้อสงสัย.
- AI detection เป็นหลักฐานเข้าคิวตรวจสอบ ไม่ใช่คำสั่งเปิดประตู.
- ต้องแยกสถานะ `command sent`, `controller acknowledged`, `physical gate feedback`, `vehicle passage` และการเปิด/ปิด session.
- การเปิดประตูต้องมีผู้ใช้ที่ได้รับสิทธิ์และเหตุผล/การอ้างอิงเหตุการณ์ตามนโยบายที่กำหนด.

## 5. เกณฑ์ยอมรับหลัก

1. Student/Teacher อ่านข้อมูลส่วนตัวของบัญชีอื่นผ่าน UI และ API ไม่ได้.
2. ข้อมูลภาพ/ทะเบียนที่ไม่มีหลักฐานหรือ confidence ตามเกณฑ์เข้าสถานะ review/unknown ไม่สร้างการอนุมัติประตู.
3. ยืนยันชั้นได้โดยไม่บังคับว่าต้องรู้ช่องจอด.
4. ช่อง offline/stale/error/conflict ไม่นับเป็นช่องว่างที่ยืนยันแล้ว.
5. การส่งคำสั่งประตูไม่แสดงว่าเปิดจริงหรือรถผ่าน จนกว่าจะมี feedback/passage evidence.
6. ทุกการเพิ่ม/แก้ไข/อนุมัติ/สั่งการบันทึก actor และเวลา.
7. ระบบแสดงแหล่งข้อมูลและเวลาอัปเดตที่ผู้ใช้ตรวจสอบได้.
8. กรณี offline, duplicate, out-of-order และ recovery ผ่านแผนทดสอบใน `TEST_PLAN.md`.

## 6. ประเด็นที่ยังไม่กำหนด

รายละเอียด protocol ของกล้อง/CiRA, ค่า threshold ที่ผ่านการวัด, หน้าต่างเวลาจับคู่รถกับช่อง, ความสามารถ buffer จริงของอุปกรณ์, exit/passage sensors, ชนิด actuator/feedback, retention และการตีความป้ายจอดเฉพาะ ต้องตรวจสอบก่อนระบุว่าเป็นข้อเท็จจริงของระบบจริง
